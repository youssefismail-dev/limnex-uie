# Q6 — the length budget deletes the tail selectively, but is not the primary cause

**Run:** 2026-09-22. `data/qry/q6_length_budget.json`, log `data/qry/q6.log`,
script `research/qry/q6_length_budget.py`. **READ-ONLY**: the frozen tokenizer
encodes corpus rows to count what training would keep. No training, no
generation, no weight, gate or corpus modified. Scope **benign**.

Checkpoint config: `max_len = 256`, `include_frame=True`, `include_language=False`
— read from `best_e5.pt` rather than from defaults, so the encoding matches the
model actually trained.

## The question, corrected before measuring

The suspicion was truncation. **It is not truncation.** `encode_corpus` deletes:

```python
if len(ids) > max_len:
    dropped += 1
    continue
```

`ModelConfig` defends this and the defence is sound — *"a truncated URL teaches
the model a URL that ends mid-path with no end token, which corrupts 1% of the
data instead of merely losing it."*

But deletion is **not neutral with respect to the tail**. The rows it removes are
the longest, and at character level a 110-character query value is one of the few
things that pushes a URL past 256 tokens. A policy losing "1% of data" can still
lose a large share of the *tail*, and the tail is the entire defect.

## Results — 400,000 rows per corpus

| | name_train (domain) | structure_train (page) |
|---|---:|---:|
| rows dropped over `max_len` | 701 (**0.175%**) | 1,731 (**0.433%**) |
| query-bearing rows | 25,442 | 41,461 |
| query rows dropped | 344 (**1.352%**) | 805 (**1.942%**) |
| enrichment vs base rate | **7.7x** | **4.5x** |

**Drop rate by the row's longest value** — deletion is anything but uniform:

| longest value | name_train rows | dropped | structure_train rows | dropped |
|---|---:|---:|---:|---:|
| 0–10 chars | 16,535 | **0.16%** | 25,153 | **0.25%** |
| 10–25 | 4,884 | 0.29% | 8,295 | 0.70% |
| 25–50 | 2,635 | 2.24% | 5,235 | 2.96% |
| 50–100 | 911 | 5.27% | 1,878 | 6.76% |
| 100+ | 477 | **41.30%** | 900 | **44.56%** |

A 258x / 178x higher drop rate at the top bucket than the bottom. **The budget is
strongly tail-selective**, and it replicates across both corpora.

**What the loss actually sees:**

| | name_train corpus | kept | structure_train corpus | kept |
|---|---:|---:|---:|---:|
| value p50 | 4 | 4 | 4 | 4 |
| value p90 | 26 | 24 | 29 | 26 |
| value p99 | **108** | **87** | **112** | **88** |
| value max | 1729 | **218** | 1866 | **225** |
| value mean | 11.78 | 9.49 | 12.22 | 9.72 |
| param count mean | 1.769 | 1.68 | 2.019 | 1.875 |
| distinct names | 9,957 | 9,096 (**−8.6%**) | 8,559 | 7,903 (**−7.7%**) |

The budget damages **all three** measured deficits at once: value length, parameter
count, and parameter-name vocabulary.

## Finding — a real contributor, NOT the primary cause

**Long values are deleted, not truncated, and deletion is heavily tail-selective.
But a substantial tail survives and reaches the loss.** The loss sees p99 = 87–88
and individual values up to 218–225 characters; the model emits p99 = 56
untruncated and 40 in production.

> **The model fails to reproduce a tail it demonstrably saw.**

Decomposing value-length p99 (`name_train`):

    corpus 108  --budget-->  87  --model-->  56  --decoder-->  40
                  -21 (31%)      -31 (46%)      -16 (24%)

The length budget is a **minority contributor at ~31%**. The model's own learning
failure is the largest single term at ~46%.

At p90 the budget's share is smaller still: corpus 26 -> kept 24 -> emitted 15,
so the budget takes 2 of 11 units (18%) and the model 82%.

## A correction to Q5 Finding 3

Q5 reported the value-length tail as **"100% model / 0% decoder"**. That was
derived from **p90** and is **p90-specific**:

- at p90: loss sees 24, model emits 15, production 15 -> decoder contributes 0;
- at p99: model emits 56, production 40 -> the decoder **does** contribute 24%.

The claim should have been scoped to p90 when made. Q5's broader conclusion — that
name concentration and value length have different model/decoder splits — stands;
the value-length split is simply percentile-dependent.

## A third candidate cause, surfaced by the data

Extreme-value rows are **sparse independently of the budget**:

    400,000 rows -> 25,442 query rows -> 477 with a 100+ char value  (0.12% of rows)
                                         280 of those survive        (0.07% of rows)

Extrapolated to the full 906,214-row `name_train`, roughly **630 surviving
examples** of a 100+ character value. That may be too little signal to learn a
distribution's extreme tail.

**This is a different cause from both the length budget and capacity, and raising
`max_len` would not address it.** It is a hypothesis generated by the measurement,
not a tested one.

## Candidate causes after Q6

| candidate | status |
|---|---|
| corpus is tail-poor | **EXCLUDED** (Q5) |
| long values truncated before the loss | **EXCLUDED** — they are deleted, not truncated |
| length budget deletes the tail | **CONFIRMED as a contributor, ~31% at p99, ~18% at p90**; replicates in both corpora |
| model fails to learn a tail it saw | **CONFIRMED as the largest term, ~46% at p99** — cause unknown |
| extreme-tail data sparsity (~630 examples) | **plausible, untested** |
| capacity (14.33M params) | **untested** |
| character-level tokenisation of long values | **untested** |
| field-scoped loss weighting | **untested** — and S3/S4 history says do not assume it |

## What this does NOT establish

1. That raising `max_len` would help materially. It would recover part of the
   tail and leave the larger term untouched, at O(n^2) attention cost and a
   larger positional embedding — and it would require retraining.
2. *Why* the model fails to learn the surviving tail. Sparsity, capacity and
   tokenisation are all untested.
3. Anything about phishing.
4. That fixing the value tail would move the gate — Q3.1's `skeleton` result
   still says shape alone reproduces the whole tell.
